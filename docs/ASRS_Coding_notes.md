Extracted and validated. The result is the Canvas "ASRS Coding Taxonomy (YAML)" — a parseable YAML tree covering all 16 pages: 8 sections (time, place, environment, aircraft, component, person, events, assessments), 102 fields, each with a cardinality tag and its allowed values list. Export it from the Canvas and drop it in your repo (e.g. data/asrs_taxonomy.yaml).
Structure decisions worth knowing:
cardinality distinguishes three field kinds: single (the form's Q1 marker — one answer, e.g. flight phase of light, primary problem), multi (Q marker — e.g. anomalies, contributing factors, results), and free (write-ins and numeric fill-ins like miss distance, experience hours, ACN). This is inferred from the Q1/Q markers — spot-check it against a real CSV export in task 7 before depending on it programmatically; confidence medium.
The events section is where the anomaly hierarchy lives — this is your HAS_ANOMALY edge vocabulary, notably anomaly_conflict (NMAC, airborne, ground-critical/less-severe) and the ground/inflight event lists. assessments.contributing_factors_situations is your HAS_FACTOR vocabulary; primary_problem is single-select, making it a good discriminative node property.
Two extraction caveats: page 7's COMPONENT section is partially nested on the form (component × manufacturer × reference × problem are cross-cutting grids, flattened here into four parallel lists), and the UAS-specific blocks are included for completeness but are irrelevant if your acquisition scope is manned aviation — ignore them or filter at parse time.
How Vibe Code should use it: load the YAML, build the field-name to allowed-values mapping, and use it in two places — (1) task 6/7 normalization and validation: split multi-value CSV cells and check every value against the taxonomy, failing loudly on unknowns, and (2) task 11 ontology: the Anomaly/Factor node value sets come straight from this file, keeping the ontology and the data validators derived from a single source.
